# Feature F3: List / Visualize Faculty Research Profiles

## What we built
For this feature, we added a public directory so anyone can browse the faculty researchers at SMU. It gives you a searchable list of everyone on the faculty, detailed profile pages for each person, and an interactive word cloud that shows research interests across the department.

## Database Updates
To make this work, we had to add a new table called `researcher_info`.
- This table stores all the extra details about a faculty member (since the base `User` table just has their basic login info).
- The columns we added are: `id` (primary key), `user_id` (this links back to the main user table), `author_id` (links to the author table, though we made this optional in the code to prevent database crashes), `highest_degree`, `orcid`, `research_fields` (which is just a comma-separated list of keywords for the word cloud), `school`, and `department`.

Quick note: for someone to actually show up in this directory, their `user_type` in the database has to be set to the researcher type (which is `1`).

## New API Endpoints

### 1. Getting the Faculty List
- **How to call it**: `GET /faculty`
- **What it does**: Returns the list of all faculty members. 
- **Filters**: You can pass in query parameters if you want to narrow things down. For example, `?search=Smith` to search by name/email, `?department=CS` for a specific department, or `?researchArea=AI` for keyword matching. It also takes `pageLimit` and `offset` for pagination.
- **What you get back**: A JSON object that looks something like this:
  ```json
  {
    "items": [
      {
        "id": 1,
        "name": "Jane Doe",
        "department": "Computer Science",
        "researchFields": "Machine Learning, AI",
        "recentPublications": [...]
      }
    ],
    "total": 1
  }
  ```

### 2. Getting a Specific Faculty Profile
- **How to call it**: `GET /faculty/:id`
- **What it does**: Grabs the full, detailed profile for a single researcher based on their user ID. It returns a JSON object with all their info and their complete publication history.

## Key Files We Added/Changed
- **Backend Model (`ResearcherInfo.java`)**: The Ebean model mapping to our new table. We ended up using an `@Transient` tag on the `author_id` column to safely bypass a schema mismatch error without having to rebuild the entire local database.
- **Backend Controller (`FacultyController.java`)**: This is where the backend APIs live (`listFaculty` and `facultyDetail`). We also put a `matchesFilters` helper method in here to handle the search parsing.
- **Frontend Controller (`FacultyController.java`)**: This grabs the JSON from the backend APIs and pushes it into the HTML templates.
- **Frontend Views**:
  - `facultyList.scala.html`: The main directory page. We pulled in a library called `jqcloud.min.js` to dynamically read the `researchFields` from the API and draw the word cloud.
  - `facultyDetail.scala.html`: The individual profile page.
